# Photo ID OCR Scan — iOS Port

Approved 19-08-2026 12:31.

Source specs: [ID_SCAN_OCR_FLOW.md](../../face-auth/ocr/ID_SCAN_OCR_FLOW.md),
[ID_SCAN_OCR_IMPLEMENTATION.md](../../face-auth/ocr/ID_SCAN_OCR_IMPLEMENTATION.md)
(Android reference implementation).

## Goal

Replace the typed name form in Quick Access enrollment with a camera step that
reads the operator's first and last name off a photo ID or staff badge. The
extracted name pre-fills two editable fields in a bottom sheet with tap-to-fill
suggestion chips; the operator confirms or corrects, taps Continue, and the name
flows into the existing 5-step face capture exactly as a typed name does today.

New self-contained feature folder `Features/OCR/`. The only edit to existing
enrollment code is `FaceEnrollmentView`'s step routing.

## Decisions (from grilling)

| # | Question | Decision |
|---|---|---|
| 1 | Scan replaces name form, or augments it? | **Replaces.** Android parity — intro → ID scan → face capture. `nameEntrySection` is deleted; the result sheet becomes the only name-entry UI, reached by a scan hit or by "Enter Manually". |
| 2 | Sheet mechanism | Existing `Core/Components/BottomSheet` modifier. Same window as the host, so none of Android's dialog-window traps apply. |
| 3 | Camera | **New `IdScanCameraService`** in the OCR folder. Back camera, no mirroring, continuous autofocus. Does not touch `FaceCameraService`, whose orientation/mirroring logic is tuned for face alignment. |
| 4 | PDF417 barcode path | **Dropped.** Pharmacists present staff IDs, not license backs. OCR only. Consequence: no authoritative path, so the two-frame confirmation and chips carry all the accuracy load. |
| 5 | Two-frame OCR confirmation + suggestion chips | Both kept. Confirmation is the accuracy lever; chips are a stated requirement. |
| 6 | Line prominence metric | **Android implementation as-is** — `heightPx` drives the badge tier. Vision returns normalized boxes, so `heightPx = boundingBox.height × framePixelHeight`. No confidence filtering. |
| 7 | Duplicate-name validation | Unchanged. A scanned name passes through the same `validateNameBeforeStarting()` gate as a typed one. |
| 8 | Session lock | Verified: iOS cannot hit Android's window-ordering bug. `SessionLockOverlay` is a root `ZStack` child at `.zIndex(1000)`; the sheet is an `.overlay` far below it in the same tree. So no force-dismiss — just stop the camera on lock, restart on unlock (table in §7.4). |
| 9 | Tests | Included by default. Full 22-case parser matrix plus analyzer tests behind a recognizer protocol. |
| 10 | Localization | English keys only in this pass. es / fr / fr-CA / hi deferred until the flow is signed off. |

### Consequences of dropping PDF417

Worth stating plainly, since it removes the spec's only authoritative path:

- Every scan is heuristic. End-to-end latency is the OCR figure (~1.0–1.5 s, two
  agreeing frames) — the ~0.3 s fast path does not exist.
- `IdScanResult.suggestions` is never empty on a hit, so the "fill fields, no
  chips" UI state from the spec's three-state table is unreachable. Two states
  remain: name + chips, and chips only.
- No AAMVA parsing, so no `DCS`/`DAC` extraction and no risk of reading DOB,
  address, or license number. The privacy scope narrows rather than widens.
- If license backs ever need supporting, `VNDetectBarcodesRequest(.pdf417)` slots
  in ahead of the OCR call in `IdCardAnalyzer.analyze` without touching the
  parser. The analyzer's structure leaves room for it deliberately.

## Architecture

MVVM, laid out like `Features/Login` — the repo's flat feature convention
(`Model/` `Repository/` `View/` `ViewModel/`), not FaceAuth's nested
`Domain/Data/Presentation`. FaceAuth is the outlier in this codebase; OCR follows
Login.

Layer responsibilities and the direction dependencies point:

```
        View                    ScanPhotoIdView, IdNameSheetContent,
          │                     IdScanCameraPreview
          │  observes @Published, sends intents
          ▼
      ViewModel                 IdScanViewModel   ← the only @MainActor type
          │
          │  owns + coordinates
          ├──────────────► Service   IdScanCameraService (frames)
          │                          IdCardAnalyzer     (per-frame orchestration)
          │
          └──────────────► Repository IdTextRecognitionRepository
                                       │  Vision, the one framework boundary
                                       ▼
                              Model    IdTextLine, IdCardName, IdScanResult
                                       IdNameParser  (pure, no imports)
```

Rules this imposes:

- **The View owns no scan state.** No analyzer, no camera, no candidate buffers in
  a `@State`. Everything the UI renders comes off `IdScanViewModel`'s
  `@Published` properties. Both views are otherwise stateless with respect to the
  scan, and take the name as a `@Binding` from the enrollment view model — the
  host owns the name, per the spec's own rule.
- **The ViewModel touches no framework.** No `import Vision`, no `VNRequest`. It
  talks to `IdTextRecognitionRepositoryProtocol` and `IdCardAnalyzer`, both
  injected, both defaulted to production instances so `IdScanViewModel()` works
  unchanged at the call site and tests pass fakes — the `LoginViewModel(loginRepository:store:)`
  pattern.
- **The Repository is the only place Vision appears.** Swapping OCR engines, or
  adding the PDF417 path later, is one file.
- **The Model is pure Swift.** `IdNameParser` imports `Foundation` and nothing
  else, which is what makes 22 unit tests possible with no device and no mocks.
- **Services are not view models.** `IdScanCameraService` and `IdCardAnalyzer`
  are plain `final class`es on their own queues, off the main actor. Only
  `IdScanViewModel` is `@MainActor`; the analyzer marshals its callback there.

Deviations from Login's exact tree, and why:

- **`Service/`** — Login has no long-lived stateful collaborators, so it needs no
  such folder. A capture session and a frame analyzer are neither model, view,
  repository, nor view model; burying them in `Repository/` would say they fetch
  data, which they don't.
- **`Model/` holds the parser, not just DTOs.** Login's `Model/` is response
  structs because its logic is server-side. Here the parsing *is* the domain
  logic and it is pure, so it belongs with the types it operates on.
- **`View/Screens/`** — mirrors `Login/View/Screens/`, with the shared preview
  wrapper one level up as `LoginLogoView` sits above `Screens/`.

Tests:

## Phase 1 — Model layer (no device)

Build and green this before anything else. Spec §5, port checklist Phase 1.

### 1.1 `Model/IdTextLine.swift`

```swift
struct IdTextLine: Equatable {
    let text: String
    /// Pixel height of the OCR line's bounding box. Load-bearing: the badge
    /// tier assumes the person's name is the largest text on the card.
    let heightPx: Int

    init(_ text: String, _ heightPx: Int = 0) { ... }
}

struct IdCardName: Equatable {
    let firstName: String
    let lastName: String
}

struct IdScanResult: Equatable {
    /// nil when no confident pair was found — the chips carry the load.
    let name: IdCardName?
    let suggestions: [String]
}
```

Positional `init` so the ported test cases read like the Kotlin ones
(`IdTextLine("Cole Paulson", 42)`).

### 1.2 `Model/IdNameParser.swift`

Direct port of spec §5.4. `enum IdNameParser` with static members — matches the
Kotlin `object` and the repo's existing `FaceAvatarRenderer` style.

Four tiers, first non-nil wins:

| Tier | Function | Matches |
|---|---|---|
| 1 | `labeledName` | `LN SMITH` / `FN JOHN`, or numbered `1 SMITH` / `2 JOHN`. **Both** labels required, so `1 MAIN ST` cannot misfire. |
| 2 | `nameLabeledName` | `Name: Cole Paulson` inline, bare `Name` with value on the next line, or stacked `First Name` / `Last Name`. |
| 3 | `commaName` | `PAULSON, COLE` — exactly two comma parts, both name-like. |
| 4 | `prominentName` | Tallest line of 2–3 name-like words. The badge case. |

Vocabulary — `STRIPPED_TOKENS` and `EXCLUDED_WORDS` ported verbatim from spec
§5.2 as `Set<String>`. The distinction is load-bearing and the spec names it the
most common porting mistake:

- **Stripped** tokens are removed from the line, the rest is still evaluated.
  `DR COLE PAULSON RPH` → `[COLE, PAULSON]` → valid.
- **Excluded** words disqualify the entire line. `MEDICAL CENTER` → rejected.

Swift-specific notes:

- Kotlin `Regex` → `NSRegularExpression`, built once as `static let`. Compiling a
  regex per line at 2.5 frames/sec is wasteful and `NSRegularExpression(pattern:)`
  throws, so construction belongs outside the hot path.
- `NAME_WORD` = `^[A-Za-z][A-Za-z'’-]*$`, ASCII as in Android. Comment records
  the `\p{L}` widening for accented names, not applied now (Android parity).
  Both apostrophe forms kept — Vision emits the typographic `’` too.
- `displayCase` ports the char-walk directly (`capitalizeNext = !c.isLetter`),
  **not** `String.capitalized`. `capitalized` lowercases after an apostrophe, so
  `O'BRIEN` → `O'brien`; the walk gives `O'Brien`. Test case 14 covers this.
- `candidateWords` keeps label-adjacent ranking first, then descending
  `heightPx`, then dedupe, then `MAX_SUGGESTIONS = 8`. Swift has no
  `distinct()` — use an ordered dedupe (`NSOrderedSet` or a seen-set reduce);
  `Set` alone loses the ranking that is the whole point.

Word-count and length rules per spec §5.5, asymmetry intact — confidence
required scales with how much autonomy the result gets:

| Function | Words | Length | Autonomy |
|---|---|---|---|
| `nameWords` (tier 4) | 2–3 | first & last ≥ 2 | fills both fields alone |
| `multiWordName` (tier 2 fallback) | 2–4 | first & last ≥ 2 | a label already vouched for it |
| `suggestionWords` (chips) | ≤ 4 | each ≥ 2 | user picks |

### 1.3 `PillCounterTests/OCR/IdNameParserTests.swift`

Swift Testing (`import Testing`, `@Test`, `#expect`) — matches
`PillCounterTests/FaceAuth`. All 22 cases from spec §5.7:

1. Badge — tallest line wins, org and role skipped
2. Two 2-word lines, differing heights — taller wins
3. `LN`/`FN` labels — middle name dropped
4. Numbered `1`/`2` + `8 100 MAIN ST` — address ignored
5. `1 MAIN ST` alone — **must not** produce a name
6. `Name: Cole Paulson` inline
7. Bare `Name`, value next line
8. Stacked `First Name` / `Last Name`
9. `Namesake Awards` — must not match the NAME label
10. No label — falls through to prominence
11. `PAULSON, COLE`
12. `DR COLE PAULSON RPH` — titles stripped
13. `COLE A PAULSON` — middle initial tolerated
14. `O'BRIEN`, `SMITH-JONES` — `displayCase` preserves punctuation
15. Empty list → nil
16. Only excluded vocabulary → nil
17–22. `candidateWords`: label-adjacent first, height ordering, dedupe, 8-cap,
    digit lines excluded, >4-word lines excluded

**Gate: all green before Phase 2.**

## Phase 2 — Repository + analyzer service

Spec §4. This is where the spec says every "scanning silently stopped working"
bug lives.

### 2.1 `Repository/IdTextRecognitionRepository.swift`

Protocol and implementation in one file, as `LoginRepository.swift` does. The
protocol is the seam spec §5.8 explicitly recommends introducing in a fresh port,
since Android has no analyzer tests for want of it:

```swift
protocol IdTextRecognitionRepositoryProtocol {
    /// Recognized lines with pixel-height boxes, or [] when nothing was read.
    /// Called off the main thread; must not return until recognition finishes.
    func recognizeText(in pixelBuffer: CVPixelBuffer) throws -> [IdTextLine]
}

final class IdTextRecognitionRepository: IdTextRecognitionRepositoryProtocol {
    static let shared = IdTextRecognitionRepository()
    private init() {}
    ...
}
```

`shared` + `private init` matches `LoginRepository`, so the analyzer's default
argument resolves the production instance and tests inject a fake.

Synchronous by design. `VNImageRequestHandler.perform` is synchronous, and a
synchronous contract makes the analyzer's single-flight logic testable without
async plumbing.

The one file in the feature that imports Vision:

- `VNRecognizeTextRequest`, `recognitionLevel = .accurate`,
  `usesLanguageCorrection = false`. Correction is trained on prose and mangles
  surnames — exactly the words that matter.
- One request object reused; a fresh `VNImageRequestHandler` per frame.
- Height conversion, the Vision-vs-ML-Kit difference:

  ```swift
  // Vision reports boxes normalized 0–1; the parser's prominence tier and the
  // ported tests both speak pixels.
  let heightPx = Int(observation.boundingBox.height * CGFloat(CVPixelBufferGetHeight(pixelBuffer)))
  ```

- `topCandidates(1)` per observation for the string; no confidence filter
  (decision 6 — Android parity).

### 2.2 `Service/IdCardAnalyzer.swift`

Ports spec §4.3 minus the barcode branch. Takes the repository through the
`LoginViewModel`-style defaulted init, so it is testable without being awkward to
construct:

```swift
final class IdCardAnalyzer {
    init(recognizer: IdTextRecognitionRepositoryProtocol = IdTextRecognitionRepository.shared)
}
```

Constants per §4.2:

```swift
private let minIntervalMs: TimeInterval = 0.4   // ~2.5 analysed frames/sec
private let recognizerTimeout: TimeInterval = 2.5
private let minSuggestionsToFire = 2
```

Responsibilities:

1. **Throttle** — drop frames arriving within 400 ms of the last attempt.
2. **Single-flight gate** — never two frames in Vision at once.
3. **Frame retain, released immediately** — the analyzer's own serial queue does
   the recognition; the camera callback returns straight after handing the buffer
   over. Under ARC a `CVPixelBuffer` is retained by the closure, so there is no
   Android-style manual bitmap recycle — but the buffer still belongs to the
   session pool, so it must not be held past the recognition call.
4. **Two-frame confirmation** — spec §6.1, barcode branch removed:

   ```
   parser returned a name?
     yes → identical to last frame's name?  yes → FIRE (name + chips)
                                            no  → store candidate, wait
     no  → ≥2 suggestions AND identical to last frame's?
                                            yes → FIRE (chips only)
                                            no  → store candidate, wait
   ```
5. **Watchdog** — 2.5 s per frame, force-releases the gate if Vision never
   returns. Frame-token guarded so a stale late completion cannot free a newer
   frame's gate or cancel its watchdog (spec §7.2).
6. **Self-pause on fire**, callback marshalled to the main queue.
7. `pause()`, `resume()` (clears **both** candidate buffers — a stale candidate
   pairing with the first frame after a pause would fire a false confirmation),
   idempotent `close()`.

Gate-release paths — the spec's six minus the two barcode ones, all four
required:

| # | Path |
|---|---|
| 1 | Recognition returned, fired or not |
| 2 | Recognizer threw |
| 3 | Buffer/handler setup failed before recognition |
| 4 | Watchdog at 2.5 s |

Miss one and the gate latches: camera streams, preview looks alive, no frame is
ever analysed again.

Concurrency: `final class`, a private serial `DispatchQueue` owning all mutable
state (candidates, token, timestamps), gate as an atomic-ish flag guarded on that
queue. State is not touched from more than one queue, so no locks needed. Deliver
the callback with `DispatchQueue.main.async`.

### 2.3 `PillCounterTests/OCR/IdCardAnalyzerTests.swift`

Against a `MockIdTextRecognitionRepository: IdTextRecognitionRepositoryProtocol`
in `PillCounterTests/Mocks/` (where the target's other mocks live), with
scriptable per-call returns, delays, and throws:

- Frame inside 400 ms is dropped; frame after it is analysed
- Second frame during an in-flight recognition is dropped
- Identical name on two consecutive frames fires once; differing names never fire
- Suggestions-only fires at ≥2 repeated suggestions, not at 1
- A throwing recognizer releases the gate — the next frame is still analysed
- Watchdog releases the gate on a hung recognizer
- Stale late completion does not free a newer frame's gate (token check)
- `resume()` clears candidates — a pre-pause candidate cannot pair post-pause
- `close()` is idempotent; no callback after close

Test synchronization via injected queues plus `confirmation(expectedCount:)`,
never `sleep`.

## Phase 3 — Camera service + preview

Spec §6, adapted to AVFoundation.

### 3.1 `Service/IdScanCameraService.swift`

Modelled on `FaceCameraService` (same `AVCaptureSession` +
`AVCaptureVideoDataOutput` + dedicated session queue shape), with ID-scan
differences:

| Concern | `FaceCameraService` | `IdScanCameraService` |
|---|---|---|
| Position | front, flippable | **back, fixed** |
| Mirroring | mirrored for front | **never** |
| Focus | default | **`.continuousAutoFocus`** + `.continuousAutoExposure` |
| Preset | 720p, `.photo` fallback | 720p — small printed text needs the detail, and per-frame OCR must stay under the 400 ms throttle |
| Pixel format | BGRA | BGRA (Vision-friendly) |
| Rotation | device orientation, no position term | same, `isVideoMirrored = false` |

Published: `isAuthorized`, `errorMessage`, `currentCameraOrientation`,
`isRunning`. Callback: `onFrame: ((CVPixelBuffer) -> Void)?`, fired on the
session queue.

Two carried-over lessons from `FaceCameraService`:

- `isConfigured` guard so a second `start()` resumes the existing graph instead
  of adding a duplicate input and leaving a black preview.
- `isObservingOrientation` guard so a re-entrant `start()` cannot stack
  orientation observers.

iOS-specific, replacing Android's periodic-autofocus loop: `.continuousAutoFocus`
is a device mode, not a one-shot, so the 1.5 s re-trigger and 2 s auto-cancel
dance is unnecessary. Set it once inside `lockForConfiguration()`.

Interruption handling, which Android has no equivalent for — the lock overlay
runs its own `AVCaptureSession`, so iOS may interrupt ours:

- Observe `AVCaptureSessionWasInterrupted` / `AVCaptureSessionInterruptionEnded`
  / `AVCaptureSessionRuntimeError`.
- On interruption end or runtime error, restart the session on the session queue.
- Publish so the view can show the RESTARTING pill.

### 3.2 `View/IdScanCameraPreview.swift`

`UIViewRepresentable` wrapping `AVCaptureVideoPreviewLayer`,
`videoGravity = .resizeAspectFill`. Same shape as `FaceCameraPreview`, including
re-asserting the rotation angle on its own connection in `updateUIView` when
`deviceOrientation` changes.

## Phase 4 — ViewModel + View

Spec §7.

### 4.1 `ViewModel/IdScanViewModel.swift`

The feature's only `@MainActor` type. Owns the scan session; **not** the name (the
enrollment view model owns that, mirroring Android's host-owns-name rule).

```swift
enum ScanStatus { case scanning, paused, restarting }
enum NameField { case first, last }

@MainActor
final class IdScanViewModel: ObservableObject {
    @Published private(set) var status: ScanStatus = .scanning
    @Published var isSheetPresented = false
    @Published private(set) var suggestions: [String] = []
    @Published var activeField: NameField = .first
    /// Duplicate-name rejection, surfaced in the sheet now that the standalone
    /// name form is gone.
    @Published var nameError: String?

    let cameraService: IdScanCameraService

    init(
        cameraService: IdScanCameraService = IdScanCameraService(),
        analyzer: IdCardAnalyzer = IdCardAnalyzer()
    )
}
```

Defaulted init as `LoginViewModel(loginRepository:store:)` — production call sites
write `IdScanViewModel()`, tests inject fakes. `cameraService` is `let` and
non-published for the preview to read; the view model forwards its
`objectWillChange` the way `FaceEnrollmentViewModel` does for `FaceCameraService`,
since a nested `ObservableObject` does not propagate its own changes and the
preview would otherwise miss rotations.

Methods: `start()`, `stop()`, `enterManually()`, `sheetDismissed()`,
`sessionLockChanged(isLocked:)`, plus the frame-stall watchdog.

The scan-result callback is where the layers meet: the analyzer fires on the main
queue, the view model writes `suggestions` / `activeField` / `isSheetPresented`
and pushes the parsed name out through the injected binding setters. No view code
participates.

Frame-stall watchdog (spec §7.4) — 4 s stale, checked every 2 s, restarts the
camera, suppressed while the sheet is open or the session is locked. A `Task`
with `Task.sleep`, cancelled in `stop()`.

**Both watchdogs are required and neither substitutes for the other:** frames
can flow while the analyzer's gate is latched (analyzer watchdog), and the gate
can be free while no frames arrive at all (frame watchdog).

### 4.2 `View/Screens/ScanPhotoIdView.swift`

```swift
struct ScanPhotoIdView: View {
    @StateObject private var viewModel = IdScanViewModel()
    @Binding var firstName: String
    @Binding var lastName: String
    let onBack: () -> Void
    let onContinue: () -> Void
}
```

Name in, name out — the host owns it. The view holds no scan state of its own:
everything it renders reads off `viewModel`.

Layout, matching the existing `FaceScanScreen` chrome so the two enrollment
camera steps read as one design:

- Full-bleed preview, no crop. The guide is **visual only** — the full frame goes
  to the recognizer. Cropping to the guide would change behaviour for loosely
  framed cards and shift the prominence tier's height comparisons.
- ID-shaped guide rectangle at 1.586:1 (ISO/IEC 7810 ID-1), sized off the
  narrower edge so iPad is sane.
- Header: back control (`PillCountingIconView` with `back_icon`, as
  `FaceScanScreen`) + title.
- Bottom card: status pill + hint text + "Enter Manually" button.
- Camera permission gate: `if !cameraService.isAuthorized { NoCameraPermissionView() }`.
  Spec §10 and §12 both call this out — a revoked permission is not a recoverable
  stall, so without the gate the watchdog spins forever on a black preview
  showing "Restarting camera…". The component already exists in
  `Features/Scanning`.

Status pill — colored dot + label, per spec §7.7. A silently dead camera and "no
ID detected yet" are otherwise indistinguishable:

| Status | Color | Meaning |
|---|---|---|
| scanning | `appColors.secondary` | Hold the ID in the frame |
| paused | `appColors.text` | Sheet open, or session locked |
| restarting | `.red` | Camera hiccup, recovering |

Sheet attached with `.bottomSheet(isPresented:onDismiss:)`. Its `onDismiss`
restarts the camera and resumes the analyzer — on iOS that is the backdrop tap,
since the component has no swipe gesture (`dismissOnBackgroundTap` defaults
`true`).

### 4.3 `View/Screens/IdNameSheetContent.swift`

Fields, chips, Continue. Takes the name bindings plus the view model, so chip taps
and `activeField` transitions are view-model methods rather than inline mutations
in the view.

Text fields: plain SwiftUI `TextField` + `@FocusState`, **not**
`FloatingLabelTextField` — that component keeps its `@FocusState` private, and
the chip-target highlight needs to know which field is focused. Styled to match.

Cursor-at-end: Android needs `TextFieldValue(text, TextRange(length))` because a
plain string binding parks the caret at 0, so the operator's first keystroke
prepends. SwiftUI places the caret at the end of a programmatically set value
already, so no equivalent is needed — verify on device against spec §12 case 5
and note the result.

Chips: `LazyVGrid` (SwiftUI has no `FlowRow`) or a simple wrapping `HStack` for
the ≤8 chips. Header text names the target field and follows `activeField` live.

`activeField` rules — spec §7.10, the invariant is *whenever a cursor exists it
is in the highlighted field*, and the two writers can never disagree because a
chip tap removes the cursor entirely:

| Event | `activeField` | Focus |
|---|---|---|
| Scan result arrives | reset to `.first` | unchanged |
| Chip tapped while `.first` | advance to `.last` | **cleared**, keyboard hidden |
| Chip tapped while `.last` | stays `.last` (repeat taps overwrite) | **cleared**, keyboard hidden |
| Field focused directly | that field | normal |

Auto-advance is what makes the common repair — OCR paired the wrong two words —
exactly two taps. Chips are "pick", not "type": a tap sets `focusedField = nil`
so the keyboard never appears.

Target highlight: primary-colored border, applied **only when no field is
focused** — visible exactly in chip-tap mode, matching Android's
`unfocused*`-only override.

Submission gate: `canContinue = !first.isBlank && !last.isBlank`, shared by the
Continue button and the keyboard's Done action. Spec §7.12 suggests extracting
this rather than duplicating it; done.

## Phase 5 — Flow integration

### 5.1 `FaceEnrollmentView` changes

Replace the `.nameEntry` onboarding step with the scan step:

```swift
private enum OnboardingStep {
    case intro
    case scanId      // was .nameEntry
}
```

- `nameEntrySection` and `nameError` — **deleted**. The sheet is the name UI now.
- `.scanId` renders `ScanPhotoIdView(firstName: $viewModel.firstName, lastName: $viewModel.lastName, onBack:, onContinue:)`.
- `onContinue` runs the existing `continueTapped()` logic unchanged: `isNameValid`
  → `validateNameBeforeStarting()` (duplicate check) → `viewModel.startEnrollment()`.
- Duplicate-name failure now surfaces **inside the sheet** (the field-level error
  slot) rather than on a separate form, since the sheet is where the name lives.
- `showsIntro` semantics unchanged: intro → scan, or straight to scan.
- Back from the scan step: to intro when `showsIntro`, else `dismiss()` — same
  rule the name form used.
- `startAnotherEnrollment()` sets `onboardingStep = .scanId`.

Orientation: the existing `OrientationLock.shared.lockForFaceCapture()` in
`onAppear` already covers the whole flow, and the ID guide is landscape-ish
inside a portrait frame on iPhone — same as Android's 320×200 dp guide in a
portrait activity. No change.

No changes to `FaceEnrollmentViewModel`, `FaceRecognitionRepository`, the Core
Data model, or the face-capture pipeline. `firstName` / `lastName` already exist
as `@Published` on the enrollment view model and already flow to
`registerUser(firstName:lastName:)`.

### 5.2 Persistence — nothing to do

Spec §9 requires the profile and its embeddings to be written in one
transaction, because a profile with no embeddings is a user who can never
authenticate. iOS already satisfies this: `registerUser` creates the row and
`saveEnrollmentEmbeddings` attaches embeddings, with `cancelEnrollment()`
deleting the partial user on any abort. Spec §9.2's double-submit guard is
already present as `FaceEnrollmentViewModel`'s state machine.

Android's process-death re-seed (spec §8.1, §5.4) has no iOS equivalent to port:
`@StateObject` is the single state holder for the whole cover, and iOS does not
restore a killed app mid-flow the way a saved-instance bundle does. The two-tier
gap that bug lives in does not exist here.

### 5.3 Privacy

Spec §9 — preserved and, without PDF417, narrowed:

- Only recognized text lines reach the parser; only name-like words leave it.
- No frame written to disk, ever. The buffer is released after recognition.
- Nothing new persisted. `FaceUserEntity` gains no columns: no DOB, no ID number,
  no ID image path. The data model enforces the scope, not just code discipline.
- No AAMVA payload is decoded at all now, so DOB/address/license-number never
  enter the process.

## On-device verification

From spec §12, minus the PDF417 cases:

**Happy paths**
1. Staff badge with org + role text → the person's name wins, org/role ignored
2. Front of a driver's license → name fills after ~1–1.5 s, chips present
3. "Enter Manually" → empty sheet, no chips, typing works, Continue gates on both fields

**Correction paths**
4. OCR pairs the wrong words → two chip taps fix it; keyboard never appears
5. Tap a field directly → keyboard appears, `activeField` follows focus; typing appends, does not prepend
6. Chip header text tracks `activeField`

**Resilience**
7. Tap the sheet backdrop → status returns to scanning, a new scan fires
8. Cover the camera → status shows restarting, recovers when unblocked
9. Leave the screen mid-scan and return → no crash, no leaked queue, scanning works
10. Rotate on iPad → preview stays correctly oriented
11. Let the session lock mid-scan → overlay covers the sheet, camera stops; unlock → scanning resumes
12. Revoke camera permission in Settings, return → permission view, not a black preview
13. Double-tap Continue → exactly one profile row
14. Scan → confirm → complete face capture → the name shows in Quick Access Users

**Privacy**
15. Inspect the store after several scans → no DOB, no ID number, no address
16. Inspect app storage → no ID images written

## Risks

| Risk | Mitigation |
|---|---|
| Vision OCR quality on staff badges differs from ML Kit; the prominence tier is tuned to ML Kit's line splitting | Vocabulary tables are the tuning surface. Phase 4 verification on real badges; extend `EXCLUDED_WORDS` for whatever org vocabulary shows up. |
| Two Vision calls/sec at 720p on older iPads may exceed the 400 ms throttle | Measure in Phase 2. Raise `minIntervalMs` if recognition runs long; the spec's own guidance. |
| Two `AVCaptureSession`s (scan + lock overlay) contending | Stop ours on lock; interruption observers restart it. Spec §7.5's iOS analogue. |
| Deleting `nameEntrySection` removes the only keyboard-only path | The sheet is reachable without a successful scan via "Enter Manually", so typing is always available. |
